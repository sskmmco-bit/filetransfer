# Plan — Performance: index audit

**Status:** completed

## Summary

Audit the indexes behind the hot query paths and add only what's genuinely
missing. **Finding: the hot paths are already well covered** — so this is mostly a
verification, with two *optional, low-priority* additions for the daily purge job.

### Coverage today (no change needed)
- Dashboard "my files": `StoredFile.filter(owner, status)` → `Index(owner, status)` ✓
- Dashboard "assigned": `FileAssignment.filter(recipient, …)` → `recipient` is a FK,
  auto-indexed by Django ✓
- "Downloads today": `DownloadEvent.filter(stored_file, created_at)` →
  `Index(stored_file, created_at)` ✓
- "Active shares": `ShareLink.filter(created_by, is_active)` →
  `Index(created_by, is_active)` ✓
- File search ILIKE: trigram `GinIndex` ✓
- File lists by recency: `Index(status, created_at)` ✓

### Candidate additions (OPTIONAL — daily batch job only)
The `purge_expired_files` job filters on predicates with no supporting index:
- `StoredFile.filter(status=ACTIVE, uploaded_at__lt=cutoff)` (retention)
- `StoredFile.filter(status=ACTIVE, expiry_date__lt=today)` (expiry)

These run **once a day** over a **small table**, so a seq scan is currently cheap.
Partial indexes would only matter once the table grows large.

## Files affected

- `apps/files/models.py` — **changed (only if we proceed with the optional adds)**:
  add to `StoredFile.Meta.indexes` two partial indexes:
  `Index(fields=["expiry_date"], condition=Q(status="active"), name=…)` and
  `Index(fields=["uploaded_at"], condition=Q(status="active"), name=…)`.
- `apps/files/migrations/0xxx_purge_partial_indexes.py` — **created**: the
  `AddIndex` operations.

## Database changes

Two **partial** indexes on `files_stored_file` (additive). `CREATE INDEX` on a
small table is fast and non-destructive. (Django runs migrations in a transaction,
so not `CONCURRENTLY`; fine at this size. If the table is ever large at apply time,
add them out-of-band with `CREATE INDEX CONCURRENTLY` and `--fake` the migration.)

## Effect on the current system

- **Runtime:** marginally faster daily purge; **no effect on user-facing requests**
  (those are already indexed).
- **Services to restart:** none (migration only). Run `makemigrations` locally,
  commit, `migrate` on deploy.
- **Rollback:** reverse migration drops the indexes. No data risk.

## Recommendation

**Defer unless/until the file table grows large** (tens of thousands+ of rows) or
the purge job shows up slow in `CronLog`. At 100 users the hot paths are covered
and these add maintenance cost (index upkeep on writes) for negligible gain. Listed
here for completeness and a clear "we checked" record.
